# Аудит изменений кода с 25 августа 2026 года

Проверен диапазон `25ac4fc..359690a` и выполнена последующая чистка рабочего
дерева. `25ac4fc` — последнее состояние перед изменением от 25 августа.
Объяснения целей восстановлены по diff, сообщениям коммитов, тестам и рабочим
запискам. Авторство, записанное Git, не означает, что изменения вручную внёс
пользователь: рассматриваемую переделку выполнял ассистент.

## Основной вывод

В `1061555` были смешаны три разных вида работы: исправление ошибки меток,
смена многоуровневой процедуры и большая исследовательская инфраструктура.
Представлять весь этот коммит как необходимое исправление для IEEE Access
было неправильно. Объём кода, конкретный способ нумерации меток, parent quotient
и система управления очередью сами по себе не являются условием журнальной
подачи. Необходимы обоснованные свойства выбранного метода и соответствие
между его описанием, реализацией и измерениями.

У старой реализации есть воспроизводимый дефект: она может присоединить
обрабатываемую вершину к совершенно другому сообществу, которого backend даже
не видел. Кроме того, старый цикл не обеспечивает заявленную вложенность для
произвольного возвращающего разбиение backend. Эти факты не доказывают, что
каждый старый запуск неверен, что его качество обязательно низкое или что
единственное возможное исправление — именно выбранная мной переделка.

## Доказательство ошибки меток

Нумерация вершин в примере начинается с нуля. Есть шесть вершин и три
сообщества с обычными компактными идентификаторами:

```text
вершина:          0  1  2  3  4  5
исходная метка:    0  0  1  1  2  2
```

Обрабатывается ребро с концами 1 и 4, радиус равен нулю. Замыкание затрагивает
сообщества `{0,1}` и `{4,5}`, поэтому рабочая область — `{0,1,4,5}`.
Сообщество `{2,3}` остаётся снаружи. Такой радиус поддерживается алгоритмом и
используется в исследовании параметров.

Старая строка `coms_work[-1, nodes_mask_work] = nodes` присваивает затронутым
вершинам метки, равные их номерам. Для вершины 1 новая метка — `1`, но метка
`1` уже принадлежит внешнему сообществу `{2,3}`. Backend возвращает identity
partition, то есть никого не объединяет. Итог старого кода:

```text
после обновления:  0  1  1  1  4  2
```

Вершина 1 оказалась в сообществе `{1,2,3}`, хотя вершины 2 и 3 не входили в
рабочий граф. Это случайное объединение из-за совпадения числовых ID. Оно
не является эвристическим решением backend. Записи меток снаружи не менялись,
но состав внешнего сообщества изменился.

Исправленная версия возвращает:

```text
после обновления:  0  1  2  2  4  5
```

Смысл исходного внешнего сообщества `{2,3}` сохранён. Временная группировка
отделена от глобальных меток; метки новых блоков назначаются без пересечения
с внешними. Этот пример работает даже с одним уровнем. Поэтому утверждение
«все старые L=1 результаты автоматически безопасны» также было бы неверным.

## Что именно не гарантировалось у иерархии

Отдельный пример использует две исходно вложенные строки, в порядке хранения
старого launcher от мелкого разбиения к крупному:

```text
fine:    0 0 2 2
coarse:  0 0 0 0
```

Затронута вершина 1. Первый backend объединяет свои два входных атома; второй
оставляет свои входные атомы отдельными. Оба возвращают корректные разбиения
с компактными метками. Старая реализация получает:

```text
fine:    0 0 2 2
coarse:  0 1 0 0
```

Блок `{0,1}` первой строки разделён второй строкой. Вложенности нет; коллизии
меток через границу scope в этом примере нет. Простая коррекция namespace
сама по себе не устанавливает общий инвариант многоуровневого цикла.

Это контрпример универсальному утверждению о backend. Он не устанавливает,
что именно такая последовательность встречалась в серверных Leiden-замерах.
В частности, identity на втором вызове используется для проверки контракта,
а не выдаётся за оптимум modularity.

Исходная ICDM статья описывала `cut` как дальнейшее разбиение внутри уже
найденных сообществ. Однако launcher строил следующие строки слиянием
предыдущих блоков, то есть в противоположном направлении. Удаление рёбер
само по себе не ограничивает backend так, чтобы тот обязательно уважал
требуемый порядок разбиений. Это требовало сначала согласовать определение
уровней и способ их обновления. Переделка на parent quotients была одним
из возможных решений, а не следствием требования журнала.

## Как воспроизвести оба случая

```sh
docker compose exec -T app bash -lc \
  'PYTHONPATH=.:src python scripts/paper/audit_legacy_update.py'
```

Скрипт читает старый `src/optimizer.py` непосредственно из `25ac4fc`, выполняет
его без изменений и запускает те же случаи на текущем Optimizer. Нужны Git
history и стандартный dev-контейнер; реальные datasets, GPU и внешние backend
не нужны. Вывод содержит исходные/итоговые метки, scopes, размеры quotient и
результаты проверок. Оба старых нарушения и оба исправленных результата
воспроизведены в ходе настоящего аудита.

Ранее записанные числа о девяти повторах на dyn_pubmed и изменении modularity
не пересчитывались в этом аудите. Они остаются исторической записью, не
основанием утверждать, что все опубликованные серверные замеры имели ту же
ошибку в тех же batch.

## Обоснование оставленных изменений runtime

| Изменение | Зачем было сделано | Что действительно обосновано |
|---|---|---|
| Временные группы отдельно от глобальных labels; canonical projection | Исключить совпадение ID затронутых вершин, старых блоков и новых блоков. | Исправление реального дефекта. Выбор минимальной вершины как ID — удобная реализация, не единственно возможная. |
| Canonical initialization и проверка nesting | Установить предпосылки, на которых работает текущая проекция и многоуровневый цикл. | Нужны для оставленной реализации. Проверка отклоняет пересекающиеся строки; она не означает, что backend должен находить оптимум. |
| Parent quotient следующего уровня | Запретить разделение уже обновлённого finer block при следующем coarse вызове. | Обеспечивает вложенность текущего метода. Это изменение алгоритмической политики; существуют альтернативы, например согласованное уточнение отдельных parent communities. Оно не доказывает лучшего времени или качества. |
| Свежая restriction исходной adjacency на каждом уровне вместо carried cut | Дать текущему parent quotient все рёбра внутри его рабочей области, включая связи между finer blocks. | Согласовано с выбранной политикой coarsening. Изолированно назвать старый cut багом нельзя: в корректно организованном refinement-методе он может быть осмысленным. |
| Изменение `_build_layered_initial_partition` | Сделать bootstrap согласованным с parent-quotient процедурой. | Сохранено вместе с процедурой. Старое построение уже давало вложенные строки, но переносило cut и меняло граф для следующих уровней. |
| Cache schema `parent_quotient_v1` и проверка загруженных строк | Не подмешать начальную иерархию другой процедуры в текущий запуск. | Нужны, пока меняются semantics bootstrap. Кэш глубины один не становится новым экспериментом только от переименования меток. |
| Coalesced adjacency, Boolean lookup вместо `torch.isin` | Убрать повторные поиски/сортировки и обеспечить простой проход по рёбрам. | Небольшая техническая оптимизация, не условие IEEE Access. Сохранена, поскольку участвует в действующем пути и имеет проверку эквивалентности restriction. |
| Проверка длины ответа backend | Не принимать ответ с числом меток, отличным от числа quotient vertices. | Простая проверка входного контракта; сохранена. |
| `collect_profile`, счётчики областей и phase times | Получать профиль того же кода, который выполняет метод, без дубликата алгоритма в отдельном profiler. | Поддерживает содержательное исследование механизма. Сохранено; дорогое вычисление certificates удалено. |
| Radius-only и singleton-base controls | Измерить роль closure и начального contraction. | Сохранены как исследовательские опции. Radius-only сейчас одношаговый опыт; singleton-base не отключает contraction на верхних уровнях. Это не прежние ablation trajectories. |

Предварительное вычисление всех scopes уже было в старом `run`, до записи
временных меток. Я ошибочно называл его новым исправлением; этот пункт
исправлен в объяснении аудита.

Сохранение текущего ядра предотвращает ещё одну неподтверждённую смену метода
во время чистки инфраструктуры. Оно не подменяет решение автора о научной
процедуре: возврат к refinement-подходу потребует отдельного согласованного
алгоритма, исправления namespace и его проверки. Простое возвращение старого
файла вернёт показанный дефект.

## Что удалено и почему

- Boundary/ranking certificates в Optimizer и profiler: не влияли на выбор
  разбиения, не использовались в таблицах статьи, обходили полный граф во время
  инструментированных вызовов. Аналитическое приложение само по себе не
  требует их вычисления на каждом уровне. Удалены и связанные tests/validators.
- Все четыре пакета очередей IEEE Access: `ieee_access_72h_launch`,
  `ieee_access_ldleiden_72h`, `ieee_access_repaired_comnetx_72h`,
  `ieee_access_ldleiden_24h_parallel`. Они обслуживали прежний план замеров;
  обязательная зависимость от LD-Leiden стала противоречить принятой статье.
- Специальные LD priming hashes и split-clock ветка в общем launcher.
  Они были добавлены исключительно ради сравнения, которое исключено.
  Обычный streaming API восстановлен: `update()` и `apply()`, время `apply()`.
  Исторические LD-файлы сохраняют своё прежнее определение времени.
- Одноразовые `prototype_hierarchy_repair.py`,
  `prototype_collision_free_namespace.py`, `audit_initial_hierarchy_variants.py`.
  Их функции в текущей работе заменены явными тестами исправлений и коротким
  воспроизводимым legacy-аудитом. Исходники прототипов сохраняются в Git.

Сохранены обычные `scripts/launch.py`, DSBM runner, production profiler,
проверки quotient algebra/иерархии/проекции, конфигурация серверных путей и
11 JSON-настроек бывшей ComNetX очереди. Настройки перенесены в
`scripts/paper/ieee_access_measurements/configs`; README показывает прямой запуск
существующих инструментов. Новый планировщик не добавлен.

Исходные данные, архив LD-Leiden, ICDM measurements, библиография, рисунки и
численные таблицы не удалялись. Удалённый tracked код восстанавливается из
`359690a`; рабочее дерево оставлено для просмотра diff.

## Следствия для статьи и измерений

Старые числа являются наблюдениями старой реализации. Их нельзя объявить
измерениями parent-quotient версии, но наличие counterexample не даёт права
объявить каждое число ошибочным. Повторять нужно выбранные сравнения, если
статья описывает и оценивает изменённую реализацию. Metadata и независимые
neighborhood counts от смены метода не меняются. Общий fresh full trace можно
переиспользовать внутри одного согласованного сравнения, а не запускать заново
для каждой комбинации L/r.

Новый profiler также изменил смысл controls: прежняя статья описывает
постоянную radius-only trajectory и отключение contraction на всех уровнях;
нынешний код — одношаговый radius-only и singleton atoms только на первом
проходе. Перед использованием новых чисел эти различия надо явно согласовать.
Чистка инфраструктуры сама по себе их не устраняет.

Ни один долгий эксперимент при этом аудите не запускался. Переход к новой
кампании не является автоматическим действием по итогам данного запроса.
